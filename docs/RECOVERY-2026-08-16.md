# Recovery — the 174 files destroyed by `git clean -fd`, 2026-08-16

**What happened.** A commit message was passed to bash as `git commit -m "…"`.
The body quoted `` `git clean -fd` `` inside backticks, so bash executed it. The
clean ran from the repo root and removed **174 untracked paths** — other lanes'
in-flight work included. Cause and prevention are in `21e28a8`; that commit's
message body also carries the only complete manifest (its 174 `Removing …`
lines), which is why it must never be amended.

**Why anything came back.** The files were untracked, so git had nothing. But
every `Write`/`Edit` any agent ever performed is recorded verbatim in the Claude
Code session transcripts under `C:\Users\BagIdea\.claude\projects\*\*.jsonl` —
a different drive the clean never touched. `scripts/_poppy_recover_from_transcripts.py`
replays those events in timestamp order (a `Write` sets the whole file, an `Edit`
applies old→new) and reconstructs the file as of its last recorded edit.

**What the tool refuses to do.** It never invents text. If a file's history
starts with an `Edit` instead of a `Write`, the base was never captured; if an
`Edit`'s `old_string` is absent from the reconstruction, an unrecorded edit
landed in between. Either way the file is marked `INCOMPLETE` and is **not**
counted as recovered. Nothing below was hand-filled to look whole.

Re-run:

```
python scripts/_poppy_recover_from_transcripts.py --list <paths> --out <dir> [--apply]
```

## 5. Standing rule this incident created

Never `git commit -m "…"` in bash. Use a quoted heredoc so nothing in the body
can execute:

```bash
git commit -F - <<'MSG'
subject

body may contain `backticks`, $(subs) and 'quotes' safely
MSG
```

And print `git status --short | wc -l` before and after every commit, so a
disappearing working tree is caught in the same breath as the commit that
caused it.
