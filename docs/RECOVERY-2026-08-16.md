# Recovery — the 175 paths destroyed by `git clean -fd`, 2026-08-16

**What happened.** A commit message was passed to bash as `git commit -m "…"`.
The body quoted `` `git clean -fd` `` inside backticks, so bash executed it. The
clean ran from the repo root and removed **175 untracked paths** — other lanes'
in-flight work included. Cause and prevention are in `21e28a8`; that commit's
message body also carries the only complete manifest, which is why it must never
be amended.

> **Correction — the manifest is 175 entries, not 174.** The first revision of
> this document said 174. That number came from `grep -c '^Removing '` over the
> message body, and a line-anchored count silently drops any entry that got
> word-wrapped onto a prose line. Two did, one at each end of the clean's
> alphabetical output:
>
> | line | how it reads in the body | entry |
> |---:|---|---|
> | 33 | `lines sat one Removing .audit_worktrees.sh` | `.audit_worktrees.sh` |
> | 207 | `Removing worktree-audit-2026-08-16.md from gone, and the manifest…` | `worktree-audit-2026-08-16.md` |
>
> Counting tokens instead of line-starts finds both:
>
> ```
> $ git log --format=%B -1 21e28a8 | grep -c '^Removing '                    # 174
> $ git log --format=%B -1 21e28a8 | grep -oE 'Removing [A-Za-z0-9._/-]+' \
>     | sort -u | wc -l                                                       # 175
> ```
>
> Both were recoverable in full and are in the recovery commit. The `.md` count
> in §2 was wrong for the same reason — the pattern used was `^docs/.*\.md`, and
> `worktree-audit-2026-08-16.md` sits at the repo root *and* mid-line, so it lost
> on both counts.

**Why anything came back.** The files were untracked, so git had nothing. But
every `Write`/`Edit` any agent ever performed is recorded verbatim in the Claude
Code session transcripts under `C:\Users\BagIdea\.claude\projects\*\*.jsonl` —
a different drive the clean never touched. `scripts/_poppy_recover_from_transcripts.py`
replays those events in timestamp order (a `Write` sets the whole file, an `Edit`
applies old→new) and reconstructs the file as of its last recorded edit.

**What the tool refuses to do.** It never invents text. If a file's history
starts with an `Edit` instead of a `Write`, the base was never captured; if an
`Edit`'s `old_string` is absent from the reconstruction, an unrecorded edit
landed in between. Either way the file is marked `INCOMPLETE` and is **not**
counted as recovered. Nothing below was hand-filled to look whole.

Re-run:

```
python scripts/_poppy_recover_from_transcripts.py --list <paths> --out <dir> [--apply]
```

## 5. Standing rules this incident created

**Never `git commit -m "…"` in bash.** Use a quoted heredoc so nothing in the body
can execute:

```bash
git commit -F - <<'MSG'
subject

body may contain `backticks`, $(subs) and 'quotes' safely
MSG
```

And print `git status --short | wc -l` before and after every commit, so a
disappearing working tree is caught in the same breath as the commit that
caused it.

**Never count a manifest with a line-anchored pattern.** A file list embedded in
prose — a commit body, a chat log, a report — can have entries word-wrapped onto
a prose line, and `^…` skips them silently while still returning a confident
round number. This document shipped once with 174/12/10 for that exact reason,
and the entry it lost, `worktree-audit-2026-08-16.md`, was hand-written prose:
the highest-value class, invisible because of a grep anchor. Extract tokens
anywhere on the line, diff the anchored count against the unanchored one, and
name every path in the delta:

```bash
grep -oE '<pattern>' body.txt | sort -u | wc -l   # not: grep -c '^<pattern>'
```

Then test each extracted path in three independent places — on disk (`test -f`),
in the commit (`git cat-file -e <sha>:<path>`), and in `git status --short`. A
path absent from all three is a real loss and must be named, never folded into a
summary count.
